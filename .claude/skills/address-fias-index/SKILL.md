# Address / FIAS index subsystem

A second pipeline keeps an address search index in sync with the external GAR (ФИАС) registry and promotes free-form "unknown" addresses to canonical FIAS ones:

- **Index key.** Each `address_index` row is keyed by the positional `normalized_index` (v3). The legacy full-text `full_index` column is **platform-owned and no longer touched by the integrator** — it is nullable and carries no unique key in the target DB, so rows the integrator writes leave it NULL. The v3 key joins all **12 GAR levels** with `|`; a present level is `"=" + normalizeValue(...)`, a NULL level is empty — so NULL is distinguishable from an empty string. `CalculateNormalizedIndex` must stay **byte-identical to the PHP `AddressIndexCalculator::calculateNormalized` mirror**, hence the explicit whitespace class `[ \t\n\r\f\x0b]` and custom trim cutset (not Go's `\s`/`strings.TrimSpace`). `AddressIndexBackfillWorker` backfills the new key on existing rows. On the platform DB the unique index is on `normalized_index` (**not** `full_index`).
- **`address_fias` identity key.** The exact address is identified by the triple **`UNIQUE(fias_id, fias_level, apartment) NULLS NOT DISTINCT`** — one `fias_id` can have several rows differing by level/apartment (apartment variants are distinct exacts). `EnsureExact`/`ResolveOrCreate` match by this triple (`IS NOT DISTINCT FROM` for the nullable columns); `fias_level`/`apartment` are computed from the `getFiasAddressById` response. **Apartment `''` vs `NULL`:** platform/PHP sometimes writes `apartment=''` where the integrator writes `NULL`, producing a duplicate exact for one `(fias_id, fias_level)`. To stop the integrator from creating such NULL-twins, the triple match in `ResolveOrCreate`/`FindByTriple` (and the `address_fias` INSERT guard) plus `AddressContragentDedupRepo.FindCandidates`' building lookup compare apartment via `NULLIF(apartment,'')` (so `''` and `NULL` collapse). Pre-existing blank rows разбирал отдельный этап `address_apartment_normalize`, снятый с эксплуатации: на проде строк с пустым `apartment` не осталось, а наполниться им нечем — платформа их больше не пишет, и непустого `apartment` на `fias_level = 11` нет ни одного. Проверочные запросы «не пора ли вернуть» — в `docs/configuration.md` §11.
- **Migration flow (`address_migration` is the queue, statuses drive it).** `address_migration` rows are seeded from `unknown_address` **before** resolve (`fias_id` is nullable, status default `NEW`), carry `fias_level`/`apartment` for triple matching and `resolve_attempts`/`next_retry_at` for retry/backoff (partial index `ix_address_migration_resolve_pickup` on `NEW`/`RESOLVING`). Status machine: `NEW → RESOLVING → { APPROVED (auto-approve at resolve, `approved_by='auto'`; light = `target_exact_id` set, heavy = NULL) | UNRESOLVED }`; then `APPROVED → MIGRATING → MIGRATED/FAILED` (`ROLLED_BACK` via `RollbackBindings`, which also `DELETE`s a `CREATE_NAME` row). The former manual-approval stage is gone: `PENDING_APPROVAL`/`PENDING_CREATE` were dropped from the status CHECK and the `Reject` repo method removed (migration `20260706120000`; old `REJECTED` rows remain valid and are still excluded from re-seeding). The resolve stage **creates no exact** — the heavy path defers creation to `AddressMigrationWorker` (`EnsureExact`). A per-row changelog (`address_migration_change`) makes migrations reversible. The migration tables intentionally have **no FK to `address`**, so deleting an address never cascade-wipes the audit trail. The migrated unknown is retained as a rollback anchor and queued into `address_pending_deletion`. **Runbook: a manual rollback (`RollbackBindings` + `MarkRolledBack`) must also `DELETE` the address's `address_pending_deletion` row** — otherwise `AddressDeletionWorker`'s pre-delete repair will repoint the restored bindings back to the target and delete the deliberately-restored address (migration `20260705120000` cleans up such leftovers for already-ROLLED_BACK rows).
- **Runtime staging (`integrator.worker.active`).** Рантайм-гейт этапа — колонка `active` строки воркера, а не отдельная таблица: `pipeline_flag` была вторым домом у того же вопроса «работает ли этап» и удалена (`20260803120400`). `WorkerStateRepo.IsActive(ctx, worker)` возвращает `(false, nil)` на отсутствующую строку — **fail-closed**, опечатка в имени не включает разрушительный этап. Гейтящиеся воркеры перечитывают колонку каждый тик фетчера и спрашивают её по **своему собственному имени** (`w.life.Name()`), поэтому этап переключается `UPDATE integrator.worker SET active=… WHERE name=…` — **без рестарта**. Two-level gating: `worker.enabled` = "worker is constructed" (нужен рестарт пода); `worker.active` = "stage is active" (следующий тик). Оба рычага в одной строке — `SELECT name, enabled, active FROM integrator.worker`. Грабли: `enabled = false` делает `active` бесполезным. Гейтятся `active`: `address_migration_resolve` (секция переименована из `address_migration_proposal` вместе со строкой — воркер спрашивает гейт по своему имени, и по старому имени строки не нашлось бы; seeded `false`), `address_deletion` (claim из `address_pending_deletion`, seeded `false` — воркер конструируется всегда, но ничего разрушительного не делает, пока не включат), `address_contragent_dedup` (seeded `false`) и `address_unknown_dedup` (seeded `false`). Отдельно от этапного гейта живёт `worker.options -> 'auto_merge'` у `address_lookup` (`WorkerStateRepo.IsOptionEnabled`, тоже fail-closed): это не этап, а ветка `mergeInto` при конфликте `normalized_index`, и читается она заново на каждой попытке слияния — чтобы разрушительную ветку можно было погасить без рестарта. Строки заводит сид миграции `20260803120000`.
