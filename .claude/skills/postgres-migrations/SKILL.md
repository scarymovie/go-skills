# Миграции PostgreSQL

PostgreSQL 18, goose 3.27+ (требует Go 1.25+).

## Формат файла — одна миграция, один файл

goose кладёт обе стороны в **один** `.sql`-файл и разделяет их аннотациями:

```sql
-- +goose Up
CREATE TABLE users (...);

-- +goose Down
DROP TABLE IF EXISTS users;
```

Парные `NNN_name.up.sql` / `NNN_name.down.sql` — это **golang-migrate, не goose**.
Если видишь такую пару в проекте на goose — либо мигратор не goose, либо файлы никогда
не применялись.

Имя: `goose create <name> sql` по умолчанию ставит префикс-таймстамп
(`20260826120000_add_users_table.sql`). Последовательная нумерация (`00001_...`) — режим
`-s`; выбирается один раз на проект. Таймстамп безопаснее при параллельной работе: две
ветки не получат один номер.

`-- +goose Down` формально необязателен, но **пиши его всегда**. Миграция без отката —
это решение «откатываться не будем», принятое молча и за всю команду.

Внутри одного файла оператор со **точками с запятой внутри тела** (функция, `DO`-блок,
триггер) надо обернуть, иначе парсер разрежет его по `;`:

```sql
-- +goose StatementBegin
CREATE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
-- +goose StatementEnd
```

## Современный синтаксис

**Identity вместо SERIAL.** `SERIAL` — специфичный для PostgreSQL хак поверх sequence;
`IDENTITY` — стандарт SQL и корректно ведёт себя при `pg_dump`.

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

`BY DEFAULT` вместо `ALWAYS` — только если действительно надо вставлять свои id
(миграция данных, импорт). В остальных случаях `ALWAYS` не даст случайно разъехаться
последовательности.

**`timestamptz`, не `timestamp`.** Голый `timestamp` не хранит зону и молча
интерпретируется в зоне сессии — то есть один и тот же ряд читается по-разному с разных
подключений.

```sql
created_at timestamptz NOT NULL DEFAULT now()
```

**`boolean`, не integer-флаг.** **`jsonb`, не `json`**: `json` хранит текст как есть,
не индексируется и разбирается на каждом обращении. **`uuid`** с
`DEFAULT gen_random_uuid()` — функция встроена с PostgreSQL 13, расширение `pgcrypto`
не нужно.

**Enum — через `CREATE TYPE`**, когда набор значений стабилен:

```sql
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');
```

Цена: добавить значение легко, **убрать или переименовать — нет** (нужен новый тип и
перенос колонки). Если набор меняется часто — строковая колонка с `CHECK` гибче.

## Размерность строковых колонок — `VARCHAR(N)`, не голый `TEXT`

Начнём с честного: **в PostgreSQL нет разницы в хранении и скорости** между
`varchar(n)`, `varchar` и `text` — это прямо сказано в документации, единственная плата
за `varchar(n)` — несколько тактов на проверку длины. Так что аргумент «varchar быстрее»
неверен, и повторять его не надо.

Ценность `VARCHAR(N)` в другом: это **проверяемое ограничение, видимое в типе колонки**.
Оно попадает в `\d`, в дампы, в интроспекцию ORM и в генерируемые DTO — то есть
становится частью контракта, а не комментарием. Голый `TEXT` означает «сюда можно
положить мегабайт», и рано или поздно кто-то положит.

| Случай | Правило | Пример |
|---|---|---|
| UUID строкой | `VARCHAR(36)` | `accepted_by VARCHAR(36)` |
| Enum строкой (с `CHECK`) | длина самого длинного значения **+ 10** | `ONLINE`(6), `OFFLINE`(7), `PAUSE`(5) → `VARCHAR(17)` |
| Свободная форма | `VARCHAR(255)` по умолчанию — **спроси, если известна более тесная граница** | `name VARCHAR(255)` |

Запас +10 на enum — чтобы следующее значение набора не требовало миграции типа.

Ревьюя миграцию, отмечай каждый `VARCHAR(255)` на колонке, где вероятна меньшая граница
(`phone`, `external_id`, `device_username`), и спрашивай реальный максимум до коммита.

Расширить границу дёшево: `ALTER TABLE ... ALTER COLUMN ... TYPE VARCHAR(M)` при `M > N`
не переписывает таблицу. Сузить — дорого и с проверкой всех строк.

## Именование и индексы

**Constraint'ы называть явно.** Сгенерированное имя нельзя предсказать, а значит нельзя
и написать `DROP CONSTRAINT` в откате.

```sql
CONSTRAINT fk_order_user_id FOREIGN KEY (user_id) REFERENCES users (id),
CONSTRAINT chk_order_total CHECK (total >= 0)
```

Имя таблицы внутри имени constraint'а — в единственном числе.

**Индекс на каждую FK-колонку.** PostgreSQL, в отличие от MySQL, **не** создаёт их
автоматически: индексируется только сторона, на которую ссылаются. Без индекса на
ссылающейся стороне `DELETE` в родительской таблице и любой `JOIN` уходят в seq scan.

```sql
CREATE INDEX ix_orders_user_id ON orders (user_id);
```

## `IF EXISTS` — в up запрещено, в down обязательно

Разное направление, разные требования, и это не противоречие.

**В `Up` гарды запрещены.** Миграция применяется ровно один раз, состояние схемы перед
ней известно. `CREATE TABLE IF NOT EXISTS` там означает «я не уверен, что было до меня» —
и прячет ровно тот случай, когда таблица есть, но другая.

**В `Down` гарды обязательны.** Откат может выполняться после частично упавшего `Up`,
когда часть объектов создана, а часть нет. `DROP ... IF EXISTS` делает откат идемпотентным.

| В Up | В Down |
|---|---|
| `CREATE TABLE` | `DROP TABLE IF EXISTS` |
| `ADD COLUMN` | `DROP COLUMN IF EXISTS` |
| `CREATE INDEX` | `DROP INDEX IF EXISTS` |
| `CREATE TYPE` | `DROP TYPE IF EXISTS` |
| `ADD CONSTRAINT` | `DROP CONSTRAINT IF EXISTS` |
| `SET NOT NULL` | `DROP NOT NULL` |

## Блокировки — из-за них миграции роняют прод

Синтаксически верная миграция может положить сервис на минуты. Три вещи, которые нужно
знать до, а не после.

**`CREATE INDEX CONCURRENTLY` не работает внутри транзакции.** А goose по умолчанию
оборачивает файл в транзакцию — значит нужен явный отказ:

```sql
-- +goose NO TRANSACTION
-- +goose Up
CREATE INDEX CONCURRENTLY ix_orders_user_id ON orders (user_id);

-- +goose Down
DROP INDEX CONCURRENTLY IF EXISTS ix_orders_user_id;
```

`NO TRANSACTION` выключает транзакцию для **всего файла**, обеих сторон. Значит в таком
файле должна быть одна операция: при падении посреди файла откатывать будет нечего.
Отдельно: неудавшийся `CONCURRENTLY` оставляет **INVALID-индекс**, который не используется
для чтения, но обновляется при записи. Его надо найти (`\d`, колонка `INVALID`), удалить
и повторить.

Обычный `CREATE INDEX` берёт блокировку на запись на всё время построения — на живой
таблице это недопустимо.

**`ADD COLUMN` с дефолтом.** С PostgreSQL 11 неволатильный дефолт **не переписывает
таблицу**: значение кладётся в метаданные и материализуется при следующей перезаписи
строки. Волатильный (`clock_timestamp()`, `gen_random_uuid()`), а также stored generated
и identity — **переписывают** таблицу целиком.

Но не путай «не переписывает» с «не блокирует»: `ALTER TABLE` берёт `ACCESS EXCLUSIVE`
в любом случае, просто держит его коротко.

**`lock_timeout` спасает от очереди.** `ACCESS EXCLUSIVE`, который ждёт долгий
`SELECT`, встаёт в очередь и **блокирует всё, что пришло после него** — включая чтения,
которые сами по себе с ним не конфликтуют. Сервис ложится не от самой миграции, а от
её ожидания.

```sql
-- +goose Up
SET LOCAL lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN note VARCHAR(255);
```

Лимит применяется к **каждой** попытке взять блокировку, единицы — миллисекунды,
по умолчанию 0 (без лимита). Ставить глобально в `postgresql.conf` не стоит: это
поведение нужно миграциям, а не всем сессиям. Правильный сценарий — упасть быстро
и повторить, а не ждать.

## Откаты, теряющие данные

Если `Down` восстанавливает колонку фиктивным значением (пустой строкой, `id::text`,
`now()`), это не полноценный откат. Задокументируй потерю прямо в файле — иначе её
примут за обратимую:

```sql
-- +goose Down
-- ВНИМАНИЕ: откат необратим. Исходные значения note не восстанавливаются.
ALTER TABLE orders DROP COLUMN IF EXISTS note;
```

Отдельный случай — `ALTER TYPE ... ADD VALUE`. Опасна не сторона отката, а **Up**:
добавленное значение нельзя использовать в той же транзакции, где оно добавлено. То
есть в одном файле «добавить значение и проставить его» не сработает — нужны две
миграции. Откат же просто невозможен: убрать значение из enum нельзя, и правильный
`Down` здесь — комментарий о том, почему он пустой.
