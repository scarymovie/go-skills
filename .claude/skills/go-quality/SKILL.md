# Качество кода и релизная сборка

Go 1.27, ниже не поддерживается — политика и перевод проекта в следующей секции.
Все команды — из корня модуля, он же корень репозитория
(скилл `go-project-structure`). Если модуль лежит в подкаталоге, каждая команда идёт через
`go -C <dir>`, а пути к файлам модуля в CI пишутся с тем же префиксом.

Тесты и их изоляция — в `go-testing`, профилирование и бенчмарки — в `go-profiling`.
Здесь только тулчейн.

## Версия Go: только 1.27

**Новый проект** объявляет `go 1.27` в `go.mod` с первого коммита. Вилки «минимум такая-то,
целевая такая-то» у нас нет.

**Существующий проект** переводится на 1.27 — это четыре команды, а не проект работ:

```bash
go get go@1.27   # поднимает директиву go в go.mod, за ней подтягивается toolchain
go mod tidy
go vet ./...     # stdversion покажет места, где код уже писался под версию новее go.mod
go test ./...
```

Дальше — `ARG GO_VERSION=1.27` в Dockerfile (скилл `docker-go`) и версия в CI-шаге установки
Go. Больше ничего: директива в `go.mod` — единственный источник правды о версии языка.

**Ставить 1.27 каждому разработчику руками не нужно.** При `GOTOOLCHAIN=auto` (это дефолт)
go-команда, увидев в `go.mod` версию выше своей, сама скачает нужный тулчейн и переключится
на него, напечатав строку вида `switching to go1.27.1`. Поэтому «у половины команды ещё 1.26»
— не аргумент держать директиву ниже: её поднятие и **есть** способ раскатить версию.

Обратная сторона важна для CI: `GOTOOLCHAIN=local` запрещает переключение, и сборка падает
с внятной ошибкой вместо тихого скачивания другого компилятора. Там, где версия ставится
явно (`actions/setup-go` с `go-version: 1.27`), нужно именно это — иначе пайплайн может
незаметно собирать не тем тулчейном, который вы в него прописали.

Почему не «целимся в 1.27, но поддерживаем 1.26»: релиз Go поддерживается, пока не выйдут
два более новых, то есть 1.26 выпадет из security-фиксов с выходом 1.28. А вилка стоит
дорого — разные наборы vet-проверок в `go test`, разные имена анализаторов, разный набор
доступных символов stdlib — и не даёт ничего, раз тулчейн переключается сам.

## Перед каждым коммитом

```bash
go fmt ./...          # форматирование
go fix ./...          # модернизаторы, см. ниже
go vet ./...          # встроенный статический анализ
go build ./...        # ловит ошибки компиляции, ничего не пишет на диск
go test ./...         # см. go-testing
```

## `go fix` — это модернизаторы, а не «починка старого API»

С Go 1.26 команда переписана с нуля. Прежние фиксеры (переписывание API времён Go 1.0)
удалены, а на их месте — набор **модернизаторов** на том же analysis-фреймворке, что
и `go vet`: они переписывают рабочий код в актуальные идиомы.

```bash
go tool fix help          # живой список анализаторов этой версии тулчейна
go tool fix help hostport # что именно делает конкретный
go fix -diff ./...        # предпросмотр без записи; ненулевой код возврата, если дифф не пуст
go fix ./...              # применить
```

Что переписывают чаще всего: `any` вместо `interface{}`, `min`/`max` вместо ручных
сравнений, `for range N` вместо счётного цикла, `slices.Contains`/`slices.Sort` вместо
ручных реализаций, `wg.Go` вместо `wg.Add`+`defer Done`, `t.Context()` в тестах,
`omitzero`, `new(expr)`, удаление ставшего лишним `x := x` в цикле.

**Один анализатор зовётся `waitgroupgo`** — до 1.27 он назывался `waitgroup`. Имя всплывает
только там, где в CI прибит конкретный флаг; такой флаг и ломается при обновлении тулчейна.
По умолчанию запускаются все, так что прибивать обычно и не нужно.

`go fix -diff ./...` в CI — рабочий гейт: код возврата ненулевой, когда есть что
переписать. Но тогда его надо прогонять локально перед пушем, иначе пайплайн будет
падать на форматировании.

## Гонки

```bash
go test -race ./...      # тесты под детектором гонок
go build -race ./cmd/app # бинарь с детектором — для ручного прогона, не для прода
```

- Нужен `CGO_ENABLED=1` и компилятор C (на Windows — MinGW).
- Замедляет в 2–20 раз, память — в 5–10 раз. Только dev и CI.
- Поддерживаемые платформы: `linux/amd64`, `linux/arm64`, `linux/ppc64le`, `linux/s390x`,
  `linux/loong64`, `freebsd/amd64`, `netbsd/amd64`, `darwin/amd64`, `darwin/arm64`,
  `windows/amd64`.
- Детектор находит только те гонки, которые **реально произошли** в прогоне. Отсюда
  `-count=10` и нагрузочные сценарии в тестах, а не один проход.

## Линтер

`go vet` — необходимый минимум, но он намеренно узкий. Всё остальное — golangci-lint
(актуальная линия v2).

```bash
golangci-lint run ./...        # проверить
golangci-lint run --fix ./...  # применить автофиксы линтеров и форматтеров
golangci-lint fmt ./...        # только форматирование
golangci-lint migrate          # конвертировать конфиг v1 -> v2 (бэкап .bck рядом)
```

**Ставить пиннутым бинарём, а не через `go install` или tool-директиву.** Причина не
вкусовая: линтер разбирает исходники фронтендом `go/analysis`, вкомпилированным той
версией Go, которой он собран. Собранный тулчейном 1.26, он не разберёт синтаксис 1.27
и будет падать на файлах, которые компилируются. Проект прямо не гарантирует работу
установки через `go install`.

Минимальный `.golangci.yml` в формате v2:

```yaml
version: "2"

linters:
  default: standard
  enable:
    - errcheck
    - govet
    - staticcheck
    - unused
    - ineffassign
    - bodyclose
    - errorlint
    - gosec
  settings:
    errcheck:
      check-type-assertions: true
  exclusions:
    generated: strict
    rules:
      - path: _test\.go
        linters: [gosec, errcheck]

formatters:
  enable:
    - gofmt
    - goimports
```

Ключевые отличия v2 от v1: обязательный `version: "2"`; `linters.default`
(`standard`/`all`/`none`/`fast`) вместо `enable-all`/`disable-all`; настройки переехали
в `linters.settings`, исключения — в `linters.exclusions`; форматтеры вынесены в
отдельную секцию `formatters` и больше не являются линтерами.

`exclusions.generated: strict` важен: без него линтер ругается на сгенерированный код,
который никто не будет править.

## Уязвимости и гигиена модуля

```bash
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...     # только достижимые по графу вызовов — мало ложных срабатываний

go mod tidy           # привести go.mod/go.sum в соответствие с импортами
go mod verify         # проверить, что скачанные модули не изменились
```

`govulncheck` разделяет находки: уязвимость, до которой есть путь вызова из твоего кода,
и уязвимость, которая просто присутствует в зависимости. Чинить в первую очередь первое.

В CI `go mod tidy` полезно прогонять с проверкой, что после него нет диффа: разъехавшийся
`go.mod` ломает сборку у следующего.

## Vet внутри `go test`

`go test` сам гоняет подмножество проверок vet перед запуском тестов. В 1.27 это
11 анализаторов: `atomic`, `bools`, `buildtag`, `directive`, `errorsas`, `ifaceassert`,
`nilfunc`, `printf`, `stringintconv`, `tests` и добавленный в 1.27 `stdversion`.

`stdversion` ловит использование символов стандартной библиотеки, которые новее, чем версия
языка в `go.mod`. Это ровно тот класс падений, который появляется в CI сразу после обновления
тулчейна на коде, который «ничего не менял»: писали под 1.27, а `go.mod` объявляет 1.25.
Он же — бесплатная проверка того, что перевод проекта на 1.27 доведён до конца.

Отключить — `-vet=off`, прогнать всё — `-vet=all`.

## Релизная сборка

```bash
CGO_ENABLED=0 go build \
  -trimpath \
  -ldflags="-s -w -X main.version=$(git describe --tags --always)" \
  -o ./bin/app ./cmd/app
```

| Флаг | Что делает |
|---|---|
| `CGO_ENABLED=0` | статическая линковка, бинарь работает в `alpine`/`scratch` без libc |
| `-trimpath` | убирает абсолютные пути сборочной машины — воспроизводимость и меньше утечки информации |
| `-ldflags="-w"` | убирает DWARF |
| `-ldflags="-s"` | убирает таблицу символов; **подразумевает `-w`**, так что `-s -w` избыточно |
| `-ldflags="-X pkg.Var=..."` | подставляет версию в переменную |

### Что на самом деле теряется при `-s -w`

Распространённое заблуждение — что `-s` ломает стек-трейсы в логах. **Не ломает.**
Трейсы рантайма, `runtime.Caller` и паники строятся из `pclntab` — таблицы, которая
входит в moduledata рантайма и не удаляется ни `-s`, ни `-w`. Имена функций, файлы и
номера строк в панике остаются на месте.

Теряется другое: ELF-таблица символов (`.symtab`) и секции DWARF. Практические
последствия — ломается интерактивная отладка (Delve и gdb не разрешают переменные и
типы), деградируют профайлеры и eBPF-инструменты, которые резолвят символы через таблицу
символов, и перестают что-либо показывать `nm`/`objdump`. Родная Go-инструментация —
pprof работающего процесса, `runtime/pprof`, трейсы — не затрагивается.

Выигрыш — около четверти размера бинаря. Для контейнерного сервиса, который отлаживают
по логам и pprof, а не под дебаггером, `-s -w` — разумный дефолт. Если в проде реально
цепляются Delve или perf-профайлером с резолвом символов, оставь `-w` без `-s`.

### Кросс-компиляция

```bash
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build \
  -trimpath -ldflags="-s -w" -o ./bin/app-linux-arm64 ./cmd/app
```

С `CGO_ENABLED=0` кросс-сборка не требует ничего дополнительного. С включённым CGO
нужен кросс-тулчейн C для целевой платформы — обычно это причина оставить `CGO_ENABLED=0`.

## Порядок перед релизом

```bash
go fix -diff ./...   # ничего не должно предлагаться
go fmt ./...
go vet ./...
golangci-lint run ./...
go test -race -count=1 ./...
govulncheck ./...
go mod tidy && git diff --exit-code go.mod go.sum
CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o ./bin/app ./cmd/app
```
