# Аудио реального времени на Go

Медийная половина. Сигнальная (SIP, SDP, почему приходит BYE) — в
`telephony-sip-diagnostics`. Профили и поиск утечек горутин — в `go-profiling`.

## Мост из двух горутин

На каждый активный звонок — ровно две горутины, по одной на направление: SIP → WebRTC
и WebRTC → SIP. Каждая — блокирующий `select`, из которого выходят **только** по отмене
контекста.

```go
func (d *Daemon) startBridges(ctx context.Context, conn *net.UDPConn, wg *sync.WaitGroup) {
	// SIP → WebRTC
	wg.Go(func() {
		for {
			select {
			case <-ctx.Done():
				return
			case p := <-fromCaller:
				raw, err := p.Marshal() // pion/rtp: ([]byte, error)
				if err != nil {
					d.log.Error(fmt.Errorf("marshal rtp: %w", err))
					continue // один битый пакет не роняет мост
				}
				select {
				case toOperator <- raw:
				case <-ctx.Done():
					return
				}
			}
		}
	})

	// WebRTC → SIP
	wg.Go(func() {
		for {
			select {
			case <-ctx.Done():
				return
			case data := <-fromOperator:
				var p rtp.Packet
				if err := p.Unmarshal(data); err != nil {
					d.log.Error(fmt.Errorf("unmarshal rtp: %w", err))
					continue
				}
				if _, err := conn.WriteTo(data, remote); err != nil {
					d.log.Error(fmt.Errorf("write rtp: %w", err))
					return
				}
			}
		}
	})
}
```

Две вещи, которые ломают этот код чаще всего. `Marshal`/`Unmarshal` в pion возвращают
ошибку — её нельзя игнорировать, но и ронять мост из-за одного битого пакета нельзя:
`continue`, а не `return`. И отправка в исходящий канал тоже должна селектиться с
`ctx.Done()` — иначе при отмене горутина повиснет на полном канале и `wg.Wait()`
не дождётся.

`wg.Go` — Go 1.25, вместо `wg.Add(1)` + `defer wg.Done()`.

## Размер канала

**Это обоснованное исключение из правила `go-code-style` «unbuffered или 1».** Там
буфер больше единицы требует обоснования — вот оно.

Небуферизованный канал означает, что отправитель ждёт получателя. В аудио это
транслируется в потерю: медленный потребитель на стороне WebRTC блокирует SIP-мост,
переполняется приёмный буфер UDP, пакеты теряются в ядре — и не видны никакому счётчику
в коде.

При 20 мс на пакет это 50 пакетов в секунду:

```go
toOperator := make(chan []byte, 50) // ~1 секунда аудио
fromOperator := make(chan []byte, 50)
```

Меньше 10 — частые блокировки и заикание. Больше 200 — буфер превращается в задержку:
разговор не терпит секунд, и «сгладить» тут нечего, устаревший пакет лучше выбросить,
чем доставить. Рабочий диапазон 50–100.

Буфер лечит короткий всплеск. Устойчиво медленный потребитель буфером не лечится —
это баг, и его надо видеть по счётчику дропов, а не маскировать размером.

## Владение каналом

Закрывает тот, кто создал. Если закрыть могут двое — рано или поздно будет
`close of closed channel`, и это паника, а не ошибка.

Когда канал передаётся между компонентами (событием, конструктором), явно фиксируй, кто
владелец: получатель канала **сохраняет** его и только читает, закрывает — создатель,
на терминальном событии звонка.

## Потери пакетов по sequence number

У RTP-пакета есть 16-битный порядковый номер, по нему считаются потери.

```go
type PacketStats struct {
	mu           sync.Mutex
	initialized  bool
	lastSeq      uint16
	packetsLost  uint64
	packetsTotal uint64
}

func (s *PacketStats) Update(seq uint16) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.packetsTotal++

	// Нулевой seq — легальное значение, поэтому «первый пакет» отмечаем флагом,
	// а не сравнением с нулём: иначе каждые 65536 пакетов один тихо не считается.
	if !s.initialized {
		s.initialized = true
		s.lastSeq = seq
		return
	}

	if gap := seq - s.lastSeq - 1; gap != 0 {
		// Вычитание uint16 переполняется само — обработка wraparound не нужна.
		// Большой gap означает переупорядочивание, а не потерю: игнорируем хвост.
		if gap < 1<<15 {
			s.packetsLost += uint64(gap)
		}
	}
	s.lastSeq = seq
}

// Snapshot отдаёт согласованный срез под одним локом. Читать поля напрямую нельзя:
// Update пишет их из горутины моста.
func (s *PacketStats) Snapshot() (total, lost uint64, rate float64) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if s.packetsTotal == 0 {
		return 0, 0, 0
	}
	return s.packetsTotal, s.packetsLost, float64(s.packetsLost) / float64(s.packetsTotal)
}
```

Логировать по порогу, а не на каждый пакет: при 50 pps на звонок лог утонет. Разумно —
раз в N пакетов проверять `Snapshot()` и предупреждать выше 1% потерь.

## Задержка — только по RTCP

Соблазн посчитать задержку из RTP-таймстампа: он в единицах медиа-часов, для PCMU/PCMA
это 8000 Гц, то есть 125 мкс на единицу. Не делай так. Медиа-часы не синхронизированы
с настенными, начальное смещение произвольно, а частота зависит от кодека (Opus — 48 кГц,
не 8). Получится число, которое меняется правдоподобно и не означает ничего.

Настоящий ответ — RTCP Sender/Receiver Report: в SR есть соответствие медиа-часов и NTP,
в RR — jitter и доля потерь от удалённой стороны. Реализации вроде pion считают RTCP,
но чтобы получить эти числа, поток RTCP надо **читать** — само по себе оно в метрики
не приедет.

Для алертинга нужен p99 jitter, а значит гистограмма. Счётчик среднего здесь бесполезен.

## Graceful shutdown — порядок важен

```go
func (d *Daemon) closeCall(c *call) {
	c.cancel()          // 1. сигнал горутинам моста
	c.wg.Wait()         // 2. дождаться, что они вышли
	close(c.toOperator) // 3. теперь писателей нет — закрывать безопасно
	close(c.fromOperator)
	_ = c.conn.Close() // 4. и только потом ресурсы
}
```

Порядок именно такой, и перепутать первые три шага — типовая ошибка. Если закрыть канал
до `wg.Wait()`, горутина моста, которая как раз собиралась в него написать, получит
`send on closed channel` — панику, а не ошибку, и упадёт весь процесс.

Обратный порядок (сначала `close`, потом `cancel`) выглядит логично («разблокируем
ждущих отправителей») и именно поэтому встречается в коде. Разблокировать их должен
`ctx.Done()` в `select`, а не закрытие канала.

## Что проверять при жалобах

**Односторонний звук.** Сначала сигнальная сторона — совпадение протокола в SDP
(`telephony-sip-diagnostics`). Если SDP в порядке, смотри счётчики обоих направлений
по отдельности: работающий мост в одну сторону и мёртвый в другую отличаются мгновенно.

**Заикание и щелчки.** Потери и джиттер по `Snapshot()`; заполнение каналов; дропы.
Если потерь нет, а заикание есть — смотри паузы GC и задержки планировщика
(`go-profiling`, execution trace).

**Растут горутины.** Их должно быть ровно 2×активных звонков. Снять базовую линию,
сделать звонок, положить трубку, сверить возврат к базовой. Не вернулось — какой-то
мост не вышел по `ctx.Done()`.

**Растёт память при стабильном числе звонков.** Обычно канал, который никто не читает,
или сохранённый пакет, удерживающий буфер.

## Грабли

- `Marshal`/`Unmarshal` игнорируются — код не собирается или молча шлёт мусор.
- Отправка в канал без `select` с `ctx.Done()` — горутина не выходит, `wg.Wait()` виснет.
- Поля счётчиков читаются мимо мьютекса — гонка, которую `-race` находит сразу.
- `time.After` в горячем `select`: с Go 1.23 несработавший таймер собирается GC и течи
  нет, но при 50 pps на звонок это всё равно таймер на каждый пакет. Переиспользуй
  `time.NewTimer` или ставь дедлайн на контекст.
- Буфер как лекарство от медленного потребителя — прячет баг и добавляет задержку.
- Задержка, посчитанная из RTP-таймстампа, — правдоподобное число ни о чём.
