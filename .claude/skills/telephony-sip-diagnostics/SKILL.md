# Диагностика SIP и медиа

Сигнальная половина диагностики. Медийная (RTP-мост, потери пакетов, счётчики) —
в скилле `telephony-realtime-audio`.

## Asterisk шлёт BYE сразу после ACK

**Симптом:** после нашего `200 OK` Asterisk присылает ACK и почти сразу (~100 мс) BYE.

### Проверять первым — SIP-заголовки в `200 OK`

Контринтуитивно, но самая частая причина — **некорректный `200 OK`**, а вовсе не
рассинхрон SRTP:

- отсутствует заголовок `Contact:`
- отсутствует `Content-Type: application/sdp`, хотя в теле SDP
- неверный `Content-Length`

Asterisk подтверждает транзакцию через ACK, но затем шлёт BYE, потому что ответа
не хватило для установления диалога: без `Contact:` некуда слать последующие
запросы внутри диалога.

### Проверять вторым — совпадение протокола в SDP

Если заголовки в порядке, сверь протокол:

- если в INVITE от Asterisk `RTP/SAVP` + `a=crypto:`, наш `200 OK` обязан нести то же самое;
- ответ `RTP/AVP` (без SRTP) там, где Asterisk ждёт SRTP, даёт немедленный BYE.

> `a=crypto` — это SDES, легаси-способ обмена ключами SRTP, и он же до сих пор
> универсальный в SIP-мире. WebRTC-сторона так не умеет: там DTLS-SRTP с
> `a=fingerprint`/`a=setup`. Если один участник моста — браузер, ключи на двух ногах
> согласуются по-разному, и сверять надо каждую ногу отдельно.

### Чеклист валидации `200 OK`

1. присутствует `Contact: <sip:...>`
2. присутствует `Content-Type: application/sdp` (когда в теле SDP)
3. `Content-Length` совпадает с размером тела
4. `m=audio ... RTP/SAVP`, если Asterisk прислал `RTP/SAVP` в INVITE
5. присутствует `a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:<key>`, если требуется SRTP

### Как читать трейс

Диагностика упирается в то, что SIP-трейс должен быть **включён всегда**, а не
поднимался постфактум: воспроизвести гонку установления диалога по требованию обычно
не выходит. Пример команд для развёртывания, где сервис логирует трейс в stdout
контейнера, — подставь свои имена файла и сервиса:

```bash
# какие SIP-заголовки ушли в 200 OK
docker compose logs app | grep -A 20 "SIP egress probe"

# тайминг: BYE меньше чем через секунду после ACK — проблема в SIP/SDP,
# а не в медиа. Дольше — смотри RTP.
docker compose logs app | grep -E "200 OK|ACK|BYE"
```

## NAT-регистрация

За NAT наш локальный порт не совпадает с тем, который видит сервер, а в `Contact:`
надо положить именно внешний. Узнать его до первой регистрации неоткуда, поэтому
регистрация двухфазная:

1. первый REGISTER с коротким `Expires=4` — узнаём NAT-порт из `rport` во Via (RFC 3581);
2. немедленная повторная регистрация с правильным портом в `Contact` и `Expires=300`.

Короткий `Expires` на первой фазе — чтобы «пристрелочная» регистрация протухла сама,
если вторая фаза не случится.

В логах ищи `"NAT port detected"` и значения `rport`.
