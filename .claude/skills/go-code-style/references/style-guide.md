# Отклонения от Uber Go Style Guide

За основу взят [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md).
Здесь **только то, где мы делаем иначе**, и то, что Uber не покрывает. Остальное —
пересказ, который и так известен; читай первоисточник.

---

## Три группы импортов вместо двух

Uber предписывает две группы: стандартная библиотека и всё остальное. Мы делим «остальное»
на внешние зависимости и свои пакеты — три группы, разделённые пустой строкой:

```go
import (
	"context"
	"fmt"

	"github.com/jackc/pgx/v5"
	"github.com/stretchr/testify/require"

	"myproject/internal/domain"
	"myproject/internal/usecase"
)
```

**Зачем.** Третья группа отвечает на вопрос, который возникает при каждом ревью: тянет ли
этот пакет что-то из соседнего слоя. В двухгрупповом варианте `myproject/internal/usecase`
теряется среди чужих модулей, и нарушение слоёв замечается только когда его начинают
искать специально.

Настраивается в golangci-lint через форматтер `gci` с секциями
`standard`, `default`, `prefix(<module>)`.

## Запрет префикса «failed to» в ошибках

Uber says «error messages should not be capitalized» и на этом останавливается. Мы идём
дальше и запрещаем **любые** вводные обороты — `failed to`, `error while`, `unable to`.

Причина видна только на длинной цепочке, поэтому её надо показать целиком:

```go
// Плохо
return fmt.Errorf("failed to create new store: %w", err)
```

Ошибка не живёт одна — она склеивается на каждом уровне:

```
failed to handle request: failed to save order: failed to create new store: connection refused
```

Половина строки — шум, повторённый трижды. Само `%w` уже означает «что-то не получилось»,
слово «failed» не добавляет ничего.

```go
// Хорошо
return fmt.Errorf("new store: %w", err)
```

```
handle request: save order: new store: connection refused
```

Читается как путь от входа к причине. Каждый уровень добавляет **где**, последний —
**что**.

Правило: сообщение — это существительное или короткая именная группа, описывающая
операцию, а не предложение о её исходе.

## «Обработай ошибку один раз» — третья ветка

Uber даёт два варианта: обработать или вернуть, и запрещает «залогировать и вернуть»
(тогда одна ошибка попадёт в лог столько раз, сколько уровней её прокинут).

```go
// Плохо — залогировали и вернули: та же ошибка окажется в логе на каждом уровне
u, err := getUser(id)
if err != nil {
	log.Error(err)
	return err
}

// Хорошо — обернули и вернули, решение принимает вызывающий
u, err := getUser(id)
if err != nil {
	return fmt.Errorf("get user %q: %w", id, err)
}
```

Мы добавляем третью ветку, которой у Uber нет: **залогировать и деградировать**. Она
применима, когда операция некритична и её провал не должен ронять основной сценарий:

```go
// Хорошо — метрики не отправились, но запрос обслужен
if err := emitMetrics(ctx); err != nil {
	log.Error(fmt.Errorf("emit metrics: %w", err))
}
```

Это тоже обработка «один раз»: ошибка дальше не идёт, потому что здесь принято решение
её проглотить. Ключевое отличие от антипаттерна — **нет `return err` после лога**.

Критерий применимости один: сценарий остаётся корректным без этой операции. Метрики,
прогрев кеша, уведомление — да. Запись в БД, списание, отправка ответа — нет.

## Что сознательно не дублируем

Интерфейсы и указатели на них, мутабельные глобальные переменные и `init()`, таблица
типов ошибок, именование `Err*`/`*Error`, `time.Duration` вместо чисел, преаллокация
контейнеров, `iota + 1` для enum, группировка объявлений, порядок функций в файле,
early return и лишний `else`, инициализация структур по именам полей, `var x T` для
нулевого значения, `nil` вместо пустого среза — всё это Uber описывает, мы согласны,
и повторять не будем.
