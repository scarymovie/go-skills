# Размер Go-файла

Размер файла — это когнитивная нагрузка. Файл, который не читается за один заход,
не ревьюится вдумчиво.

## Пороги

| Строк | Что значит | Что делать |
|---|---|---|
| ≤ 300 | Норма | Ничего |
| 300–500 | Пора задуматься | Прогнать по вопросам ниже до того, как добавишь ещё код |
| 500+ | Плохо | Не дописывать в этот файл, сначала разделить |
| 1000+ | Технический долг | Не мержить PR; разделить до ревью, а не после |

Вопросы на пороге 300–500 — не смешались ли зоны ответственности, не выделяется ли
отдельный концепт, не пора ли вынести вспомогательные функции. Если ответ «да» хотя бы
на один, дели сейчас: аргумент «ещё пятьдесят строк не критично» — это и есть механизм,
которым файл доезжает до тысячи.

## Одна реализация интерфейса — один файл

Главное правило файла, и оно перевешивает пороги выше. Если структура реализует
интерфейс, её методы **не разносятся** по файлам: читатель должен видеть контракт
целиком, а компилятор не подскажет, что половина методов уехала.

Вместе с реализацией держи её конструктор и приватные хелперы, специфичные именно
для неё. Отдельно выноси вспомогательные структуры (Mapper, Validator, Cache), общие
утилиты и независимые компоненты.

## Признаки, что пора делить

**Структурные:** больше трёх типов в файле; больше десяти функций/методов; смешаны
разные уровни абстракции; CRUD и бизнес-логика в одном сервисе.

**Когнитивные:** не получается объяснить назначение файла за минуту; приходится
постоянно скроллить; нужно держать в голове больше трёх концептов.

## По чему делить

1. **По зонам ответственности** — CRUD отдельно от бизнес-логики, валидация отдельно
   от обработки, HTTP-хендлеры отдельно от usecase, queries отдельно от commands.
2. **По уровням абстракции** — публичный API отдельно от internal-хелперов, домен
   отдельно от инфраструктуры.
3. **По частоте изменений** — часто меняющийся код отдельно от стабильного, разные
   bounded context отдельно.

## Исключения

Больше 300 строк допустимо для сгенерированного кода (но его и не редактируют руками),
таблиц данных и констант (но подумай про вынос в YAML), тестов и реализации интерфейса
с 15+ методами — последнее прямо конфликтует с правилом «>10 методов» выше, и правило
одного файла побеждает: вместо разделения вынеси вспомогательную логику в отдельные
структуры.

Даже в исключениях 500 строк — потолок.

## При генерации кода

- Не выдавать файл длиннее 300 строк одним куском.
- На файле длиннее 250 строк — предлагать разделение, а не «добавим ещё функцию».
- Перед генерацией заведомо большого кода — спросить, как его разложить.
- Методы одной реализации интерфейса — всегда в один файл.
