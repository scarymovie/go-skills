# Работа с доменными событиями

Проект 100% событийный (см. CLAUDE.md, скилл go-testing). Этот скилл — про **контракт самого
события**, а не про шину. Шина (`internal/events/topic.go`) — тупой pub/sub; смысл и инварианты
живут в конструкторах `New<Event>` в `internal/domain/events/`.

## Главный принцип: событие не опережает состояние

**Событие — это запись факта перехода, который УЖЕ произошёл и УЖЕ сохранён в БД.**
Не «команда сделать», не «обещание». Если опубликован `CanceledCallAppear` — значит звонок
уже `Canceled` и уже persистнут. Подписчик может доверять этому факту.

Отсюда два правила.

### Правило 1 — конструктор валидирует инвариант (статус)

Конструктор `New<Event>` проверяет, что переданный объект в статусе, соответствующем смыслу
события. Это единственная точка валидации (как в скилле go-structs: «валидация только в конструкторе»).

```go
func NewCanceledCallAppear(call domain.Call) *CanceledCallAppear {
	if call.Status() != domain.CallStatusCanceled {
		// инвариант продюсера: перед публикацией звонок ПЕРЕВЕДён в Canceled и persистнут.
		panic("CanceledCallAppear: call must be Canceled, got " + string(call.Status()))
	}
	return &CanceledCallAppear{call: call, occurredAt: time.Now().UTC()}
}
```

Карта инвариантов по статусу звонка (применять по смыслу события, не механически):

| Событие | Требуемый `call.Status()` |
|---|---|
| `IncomingCallAppear` / `OutboundCallAppear` / `OutboundCallRequested` | `Pending` |
| `OperatorAcceptedCall` / `CallPreparedForOperator` / `OperatorJoinedCall` / `CallReadyForOperator` | `Accepted` |
| `ActiveCallAppear` / `OperatorActive` | `Active` |
| `CallEnded` | `Ended` |
| `CanceledCallAppear` | `Canceled` |

> События, которые НЕ фиксируют переход статуса, а несут транспорт (каналы в
> `CallReadyForOperator`, SDP в `OperatorJoinedCall`), всё равно проверяют статус несущего
> звонка — но дополнительных инвариантов на сам транспорт не навешивай, если нет нужды.

### Правило 2 — продюсер: transition → persist → construct → publish

Перед публикацией продюсер обязан:

1. **Перевести** доменный объект в целевой статус — иммутабельно, новым конструктором
   (см. скилл go-structs; пример — `inbound.go:95` строит `accepted`-копию через `NewIncomingCall`).
2. **Persистнуть** переход в БД через репозиторий (`incomingCallRepo`/`outboundCallRepo`).
3. **Сконструировать** событие (тут инвариант из Правила 1 и проверится).
4. **Опубликовать** в топик.

```go
canceled := domain.NewIncomingCall(/* ...та же копия..., */ domain.CallStatusCanceled, /* ... */)
if err := d.incomingCallRepo.SetCanceled(ctx, canceled.Id(), time.Now().UTC()); err != nil { /* ... */ }
events.CanceledCallAppearTopic.Publish(*events.NewCanceledCallAppear(canceled))
```

## Почему так, а не «ещё один подписчик»

Соблазн при «статус не сохраняется» — повесить отдельного подписчика на `CanceledCallAppear`,
который зовёт `SetEnded`. **Не делать.** Это плодит подписчиков, разносит причину события и его
персистенцию по разным местам и создаёт окно, где БД отстаёт от опубликованного факта (ровно баг:
accept успевал принять «мёртвый» звонок, пока статус был ещё `pending` — см. скилл go-testing,
раздел «Известные баги»).

**Подписчики — для РЕАКЦИЙ на факт** (открыть/закрыть WebRTC-peer, поднять/погасить RTP-сессию,
уведомить оператора по WS), а не для записи самого факта перехода. Запись перехода — ответственность продюсера
(Правило 2), а его корректность стережёт конструктор (Правило 1).

## panic vs error в конструкторе

- **panic (по умолчанию для этих инвариантов).** Невалидный статус = баг продюсера, который
  обязан был сделать transition+persist. Fail-fast, сигнатура `New<Event>` остаётся `*T`, не
  ломаются все места публикации. Согласуется с каноническим примером скилла go-structs (`panic` в
  конструкторе). В тестах паника проверяется `require.Panics`, а под тестом изолируется
  `recoverAsFailure` (см. go-testing, Паттерн 4), чтобы не уронить весь пакет.
- **error** — если есть легитимный путь, где продюсер может получить ещё-не-переведённый объект и
  должен обработать это, а не падать. Тогда `New<Event>(...) (*T, error)` и обработка на каждом
  publish-сайте.

## Как это тестировать

- **Красный/зелёный на инвариант конструктора:** `New<Event>` с неверным статусом → `require.Panics`
  (или ошибка); с верным → ок. Чистый unit, без БД.
- **Продюсер (Паттерн 2 из go-testing, реальный Postgres):** прогнать продюсера/хендлер, проверить,
  что в БД статус терминальный И событие опубликовано — порядок «БД раньше или одновременно с
  событием» гарантирован Правилом 2.
- Не публиковать «голое» событие в тесте в обход Правила 2: если конструктор валидирует статус,
  публикация требует сперва перевести+persистнуть звонок — тест зеркалит продюсера.
