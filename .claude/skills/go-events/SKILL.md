# Контракт доменного события

Go 1.27 (минимум 1.26).

Этот скилл — про **смысл события**: что оно утверждает и кто имеет право его опубликовать.
Реализация шины — скилл `eventbus` (очередь, порядок доставки, backpressure, shutdown), он ничего
не знает о домене. Пример на реальном проекте — `references/example-asterisk.md`.

## Главный принцип: событие не опережает состояние

**Событие — запись факта перехода, который УЖЕ произошёл и УЖЕ сохранён.** Не «команда сделать»,
не «обещание». Если опубликован `OrderCanceled` — заказ уже в статусе `Canceled` и уже
закоммичен. Подписчик может доверять факту, не перепроверяя БД.

Отсюда три следствия.

### Конструктор стережёт инвариант

`New<Event>` проверяет, что переданный объект в статусе, который соответствует смыслу события.
Это единственная точка валидации (скилл `go-struct`: валидация только в конструкторе). Без неё
инвариант приходится перепроверять в каждом подписчике.

```go
func NewOrderCanceled(order domain.Order) (*OrderCanceled, error) {
	if order.Status() != domain.OrderStatusCanceled {
		return nil, fmt.Errorf("order %s must be Canceled, got %s", order.ID(), order.Status())
	}
	return &OrderCanceled{order: order, occurredAt: time.Now().UTC()}, nil
}
```

### Продюсер: transition → persist → construct → publish

1. **Перевести** объект в целевой статус — иммутабельно: новый объект, а не мутация на месте
   (скилл `go-struct`).
2. **Persистнуть** переход через репозиторий.
3. **Сконструировать** событие — здесь инвариант из пункта 1 и проверится.
4. **Опубликовать** в топик.

```go
canceled, err := order.Cancel(time.Now().UTC())
if err != nil {
	return fmt.Errorf("cancel order: %w", err)
}
if err := r.orders.Save(ctx, canceled); err != nil {
	return fmt.Errorf("persist canceled order: %w", err)
}
evt, err := events.NewOrderCanceled(*canceled)
if err != nil {
	return fmt.Errorf("build OrderCanceled: %w", err)
}
r.orderCanceled.Publish(*evt) // *eventbus.Publisher[events.OrderCanceled]
```

Шаги 2 и 4 не переставляются местами: публикация раньше коммита означает, что подписчик увидит
факт, которого в БД ещё нет, — и, пойдя за деталями в репозиторий, прочитает старый статус.

### Подписчики реагируют на факт, но не записывают факт

Соблазн при «статус не сохраняется» — повесить отдельного подписчика, который зовёт `SetCanceled`.
**Не делать.** Это разносит причину события и его персистенцию по разным местам и оставляет окно,
где БД отстаёт от уже опубликованного факта.

Подписчик — для **реакции**: закрыть соединение, погасить сессию, уведомить, отправить письмо.
Запись перехода — ответственность продюсера, её корректность стережёт конструктор.

## Конструктор события возвращает ошибку, а не паникует

Владелец правила — скилл `go-code-style`, здесь оно не переопределяется: **`New<Event>` возвращает
`(*T, error)`**. Невалидный статус — действительно баг продюсера, но паниковать на нём нельзя:
объект приходит из БД или из запроса, а не из литерала в коде.

`panic` допустим только в `Must`-обёртке над литералами, а для события это ровно один случай —
билдер тестовых фикстур: package-level литерала события не бывает, в отличие от
`var systemUser = MustNewUser(...)` в `go-struct`.

```go
// MustNewOrderCanceled — только для фикстур: order собран литералом в тесте, и ошибка означает
// опечатку в самом тесте. На объекте из БД или из запроса — NewOrderCanceled.
func MustNewOrderCanceled(order domain.Order) *OrderCanceled {
	evt, err := NewOrderCanceled(order)
	if err != nil {
		panic(err)
	}
	return evt
}
```

Ошибку конструктора продюсер не глотает и не «чинит» подстановкой статуса: она означает, что
transition или persist не сделаны. Вернуть вверх, событие не публиковать.

## Дырка правила: dual-write между коммитом и публикацией

Порядок persist → publish убирает одну гонку и создаёт другую. Между коммитом транзакции и
`Publish` есть окно. Умер процесс в этом окне (паника, OOM, рестарт при деплое) — **факт в БД есть,
подписчики о нём не узнали никогда**: retry внутри процесса не спасает, процесса уже нет. Отказ
самого `Publish` (брокер лёг, очередь переполнена) — случай легче: процесс жив, ретрай возможен.

Последствие — не «потерянное сообщение», а рассогласованное состояние: заказ `Canceled`, но деньги
не возвращены и смежная система считает заказ живым; расхождение молчит, пока его не найдут руками.
Перестановка шагов 2 и 4 не помогает — она меняет потерю на фантом (см. выше).

### Идемпотентных подписчиков хватает, когда шина переживает рестарт

Шина хранит недоставленное и подтверждает обработку (at-least-once) — тогда недоставленное доедет
ретраем, а от дублей защищает идемпотентность подписчика. In-process `eventbus` так не умеет: для
него этой ветки нет вовсе, остаётся outbox или осознанно принятая потеря. Условия:

- у события есть **стабильный ключ** — id агрегата плюс тип перехода, или id записи о переходе.
  Не `time.Now()` и не uuid, сгенерированный заново на каждой попытке;
- обработчик проверяет «уже сделано» перед действием либо опирается на upsert / unique-constraint;
- повторное применение дешевле пропуска.

Так закрываются реакции, которые безопасно повторить: пересчёт кеша, повторный WS-push, закрытие
уже закрытого соединения. Чего не закрывает даже брокер — смерть до `Publish`: ретраить нечего,
вызова не было.

### Нужен transactional outbox, когда

Пропуск события стоит дороже, чем сложность инфраструктуры: списание денег, вызов внешней системы,
выпуск документа. Тогда намерение опубликовать коммитится в **той же транзакции**, что и переход.

```go
// в outbox кладётся DTO события, а не доменный объект: у него приватные поля
payload, err := json.Marshal(events.OrderCanceledDTO{OrderID: canceled.ID()})
if err != nil {
	return fmt.Errorf("encode OrderCanceled: %w", err)
}
// одна транзакция: переход и запись в outbox коммитятся вместе или не коммитятся вовсе
if err := r.trm.Do(ctx, func(ctx context.Context) error {
	if err := r.orders.Save(ctx, canceled); err != nil {
		return err
	}
	return r.outbox.Add(ctx, outbox.Record{
		Key:     canceled.ID() + ":canceled", // стабильный ключ идемпотентности
		Type:    "OrderCanceled",
		Payload: payload,
	})
}); err != nil {
	return fmt.Errorf("cancel order: %w", err)
}
```

Отдельный воркер читает неотправленные строки и публикует, помечая отправленные. Смерть в любой
точке = строка осталась неотправленной, её подхватит следующий проход. Границы транзакции — скилл
`pgx-txmanager`: запись в outbox обязана лечь в тот же `Do`, что и переход, иначе смысла нет.

Цена: доставка становится at-least-once **по построению** — воркер мог опубликовать и умереть до
пометки, так что подписчики всё равно обязаны быть идемпотентными. Плюс порядок событий теперь —
порядок строк outbox, а не вызовов `Publish`, и к задержке добавляется лаг воркера.

**In-process шина без outbox — всегда at-most-once на границе процесса.** Это допустимый выбор, но
он должен быть выбором, а не побочным эффектом: напиши в комментарии у продюсера, что теряется при
рестарте.

## Инвариант тестируется юнитом, продюсер — на реальной БД

- **Инвариант конструктора** — чистый unit без БД: неверный статус даёт ошибку, верный — событие.
- **Продюсер** — на реальном Postgres (скилл `go-testing`, Паттерн 2): прогнать продюсера и
  проверить, что в БД целевой статус И событие опубликовано.
- Не публиковать «голое» событие в обход продюсера: конструктор валидирует статус, значит тест
  обязан сперва перевести и сохранить объект — тест зеркалит продюсера.
- **Идемпотентность подписчика** проверяется прямо: доставить одно и то же событие дважды и
  убедиться, что эффект однократный.
