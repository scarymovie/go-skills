# Тестирование Go-сервисов

Go 1.27, ниже не поддерживается (политика версий — скилл `go-quality`).

Тестируем **то, что код реально делает**, на реальной инфраструктуре, а не на моках всего
подряд. Мок своего же компонента проверяет, что мок работает.

## Выбор вида теста

| Что делает код | Какой тест | Нужна БД |
|---|---|---|
| Чистая функция, маппер, разбор формата | table-driven unit | нет |
| Пишет/читает in-memory хранилище (registry, кеш) | тест в его пакете | нет |
| Пишет в БД через репозиторий | тест на реальном Postgres | да |
| Цепочка HTTP → событие → потребитель → БД | интеграционный | да |

Не гнаться за сплошным покрытием — покрывать осмысленные эффекты. Вводить тесты поэтапно,
от дешёвых к дорогим: сначала чистое ядро, потом репозиторий, потом цепочка.

## Граница: тестируй свой шов

Чужие системы не поднимаем. Тестируем свой код там, где он с ними стыкуется.

- **Вход крафтим** — конструируем тот объект, который получает наш код: разобранный
  запрос, типизированный DTO, событие. Продюсера (браузер, внешний сервис, брокер)
  не запускаем.
- **Выход проверяем по своим эффектам** — запись в БД, опубликованное событие, ответ
  хендлера. Внешние выходы — записывающий дубль **нашего** интерфейса; протокольные
  кишки чужой системы не проверяем.
- **БД — не внешний сервис, а наше хранилище.** Её поднимаем по-настоящему.

Стабов должно быть считанное число, и каждый — с обоснованием, почему его нельзя поднять
(обычно: внешняя авторизация, платный API). Репозитории, шину, воркеры, реестры — не мокаем.

## Инструменты и конвенции

- stdlib `testing` + `testify`: `require` — остановиться на первой ошибке, `assert` —
  когда есть смысл продолжить и увидеть все расхождения.
- Table-driven там, где кейсов много; `t.Run` на подкейс, чтобы имя падения было читаемым.
- Доменные модели строить через их `New*`-конструкторы, а не литералом структуры: тест
  должен ломаться, когда ломается инвариант конструктора.
- Логгер в тестах — на `io.Discard` (или `slog.DiscardHandler`, Go 1.24).
- **`t.Cleanup` вместо `defer` в хелперах.** `defer` в хелпере срабатывает при выходе
  из хелпера, а не из теста, и с `t.Parallel()` ведёт себя не так, как ожидается.
  `t.Cleanup` регистрирует уборку на сам тест.
- `t.TempDir()`, `t.Setenv()` — вместо ручного создания и восстановления.

## Детерминизм и время

Тест, который лечится увеличением таймаута, не починен. Порядок предпочтений:

**1. `testing/synctest` — дефолт для всего, что зависит от таймеров.** GA с Go 1.25.
Внутри «пузыря» время фейковое: когда все горутины пузыря заблокированы, часы
перепрыгивают к ближайшему таймеру. Тест на пятиминутный бэкофф идёт микросекунды
и не флачит.

```go
func TestRetryBackoff(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		c := newClient(withBackoff(time.Second, time.Minute))
		go c.run()

		synctest.Wait()             // все горутины пузыря встали на таймерах
		synctest.Sleep(time.Minute) // промотать минуту фейковых часов и снова дождаться
		// ...проверки: сколько было попыток и с какими интервалами
	})
}
```

Функций ровно три, и больше не нужно:

- `synctest.Test(t, f)` — гоняет `f` в пузыре и ждёт завершения всех его горутин;
- `synctest.Wait()` — блокирует, пока все остальные горутины пузыря надёжно не встанут;
- `synctest.Sleep(d)` — промотать `d` по часам пузыря и следом сделать `Wait`. Добавлена
  в 1.27 и заменяет связку `time.Sleep(d)` + `synctest.Wait()`, которую до этого писали
  руками; забытый `Wait` во второй половине связки — классический источник флака.

`synctest.Run` из экспериментального API 1.24 не существует: он удалён в 1.26. Компилятор
это поймает сразу, но знать стоит — статьи и ответы на Stack Overflow до сих пор написаны
под него, и переписывать их надо на `synctest.Test`.

**Ограничение, из-за которого synctest не универсален:** пузырь считает горутину
заблокированной, только если она встала на канале, мьютексе или таймере пузыря.
Горутина, ждущая настоящий сетевой ответ или запрос к Postgres, «надёжно
заблокированной» не считается. Поэтому synctest — для логики с таймерами, а не для
тестов с реальной БД.

**2. `require.Eventually` — для тестов с реальной инфраструктурой.** Там, где побочка
приезжает из чужой горутины и synctest неприменим.

**3. Таймауты инъектируются, а не хардкодятся.** Если воркер опрашивает раз в 500 мс,
тест передаёт свои 50 мс, а не ждёт полсекунды. Значение приходит параметром
конструктора.

Реальный `time.Now()` в проде означает, что окна в тестах нельзя задавать литералами дат:
окно, историческое сегодня, вчера было будущим. Считать от текущей даты.

## Паттерн 1 — чистое ядро и in-memory

Проверяем эффект напрямую, без инфраструктуры. Здесь же — `t.Parallel()` без оговорок.

```go
func TestOfferRegistry_DeleteRemovesOffer(t *testing.T) {
	t.Parallel()
	reg := NewOfferRegistry()
	ctx := t.Context() // Go 1.24: отменяется автоматически по завершении теста

	require.NoError(t, reg.Save(ctx, "call-1", "offer"))
	require.NoError(t, reg.Delete(ctx, "call-1"))

	_, err := reg.FindByCallID(ctx, "call-1")
	require.ErrorIs(t, err, ErrNotFound)
}
```

Покрывать edge: перезапись по тому же ключу, удаление несуществующего (no-op),
согласованность нескольких индексов, идемпотентность флагов.

## Паттерн 2 — реальный Postgres

Хелпер `internal/testdb` даёт три вещи: `Pool(t)` — singleton из `TEST_POSTGRES_DSN`,
а без переменной `t.Skip` (тесты на хосте без БД просто пропускаются); `RunInTx(t, pool, fn)` —
транзакция с гарантированным откатом; `Truncate(t, pool)` — `TRUNCATE ... RESTART IDENTITY CASCADE`.

### Изоляция выбирается по числу соединений

| Тест | Соединений | Изоляция | `t.Parallel()` |
|---|---|---|---|
| Чистый repo-CRUD | одно | `RunInTx` | да |
| Воркер (пишет на своём ctx мимо tx) | несколько | `Truncate` | нет |
| Гонка (N горутин через пул) | несколько | `Pool` + уникальные id | нет |

**Почему так.** Транзакция pgx привязана к одному соединению, а соединение не
потокобезопасно. Воркер пишет из своей горутины на собственном контексте — `RunInTx`
её не поймает, коммит уйдёт мимо транзакции. Тест на гонку по смыслу требует нескольких
реальных соединений. Для обоих tx-откат не годится → `Truncate` или уникальные id.

**Отсюда же `-p 1` при прогоне.** Пакеты делят один Postgres, а `TRUNCATE` берёт
ACCESS EXCLUSIVE и подерётся с открытой транзакцией соседнего пакета. `-p 1`
сериализует **пакеты**; параллелизм внутри пакета (`t.Parallel`) продолжает работать.

### Транзакционный repo-тест

Репозитории внутри `fn` **обязаны использовать переданный `ctx`** — из него getter
достаёт транзакцию. Репозиторий, взявший другой контекст, запишет мимо и не откатится.

```go
func TestIncomingCallRepository_TryAccept_FirstWinsSecondLoses(t *testing.T) {
	t.Parallel()
	pool := testdb.Pool(t)
	calls := NewIncomingCallRepository(pool)

	testdb.RunInTx(t, pool, func(ctx context.Context) {
		call := seedPendingCall(ctx, t)

		first, err := calls.TryAccept(ctx, call.ID(), "op-1")
		require.NoError(t, err)
		require.True(t, first)

		second, err := calls.TryAccept(ctx, call.ID(), "op-2")
		require.NoError(t, err)
		require.False(t, second) // звонок уже принят
	})
}
```

Гонка на том же `TryAccept` — уже **не** в `RunInTx`: одна tx = одно соединение.

## Паттерн 3 — HTTP-граница

Хендлер зовём **напрямую**, не через `ServeHTTP` и не через листенер: `httptest.NewRequest`
и так in-memory, сокета нет. Тело подаём маршалом типизированного DTO, а не строковым JSON —
иначе тест переживёт переименование поля.

Подписка на выходной топик — **до** вызова, иначе событие потеряется. Проверяем обе стороны:
и запись в БД, и факт публикации.

Негативные ветки ассертим симметрично: код ответа **и** что события **не** было
(короткий `select` с `default`).

## Конкурентность в тестах

- **`require` и `t.FailNow` нельзя звать из не-тестовой горутины** — они зовут
  `runtime.Goexit`, который убьёт эту горутину, а не провалит тест. Собирать результаты
  в слайс по своему индексу, ассертить после `wg.Wait()` в основной горутине.
- Гонку заводить от общего барьера: горутины ждут `<-start`, тест делает `close(start)`.
  Без барьера они стартуют по очереди и гонки не будет.
- `wg.Go(func(){...})` (Go 1.25) вместо `wg.Add(1)` + `defer wg.Done()`.

## Тесты, которые зеленеют впустую

Самый дорогой класс ошибок: тест проходит и ничего не проверяет.

- **Проверь, что то, на чём тест держится, вообще запустилось.** Если тест про поведение
  фоновой горутины, а она из-за порядка настройки не стартовала, тест выродится в проверку
  простаивающего объекта — и будет зелёным. Ассертить наличие горутины явно.
- **Не сверяй порог с константой, которая его задаёт.** Границы в тесте — литералы.
  Сверка значения с самим собой не проверяет ничего.
- **Если проверяешь окно между двумя событиями, поток должен быть управляемым.** Со
  «скриптованным» источником сообщения улетают подряд, и промежуточное состояние наблюдать
  нечем.
- **Инвариант — хелпером на каждый кейс таблицы.** Один `assertInvariants(t, got)`,
  вызываемый в каждом кейсе (Σ частей равна целому, границы не разъезжаются), ловит то,
  на что не написали отдельную ассерцию.

## Красные тесты и паники

Сначала тесты, потом починка прода. Красный тест — это найденный баг, его не подгоняют
и не глушат `t.Skip`.

Прогон не останавливается на первом провале: `require`/`t.Fatal` роняют только свой тест.
**Обрывает только `panic`** — она крашит тест-бинарник всего пакета и прячет остальные
тесты. Поэтому панику прод-кода под тестом изолируем в обычный провал:

```go
func recoverAsFailure(t *testing.T) {
	t.Helper()
	if r := recover(); r != nil {
		t.Errorf("прод-код под тестом паникует (баг, чинится отдельно): %v", r)
	}
}
```

Первой строкой в таком тесте — `defer recoverAsFailure(t)`. Работает, только если вызов
синхронный: паника в другой горутине этим не ловится, её `recover` должен стоять там же.

## Прогон

Все команды — из корня модуля, он же корень репозитория (скилл `go-project-structure`).

```bash
go test ./...                    # весь модуль
go test -race ./...              # обязательно для всего конкурентного
go test -race -count=1 ./...     # -count=1 отключает кеш результатов
go test -count=10 ./pkg/         # ловит флаки
go test -shuffle=on ./...        # ловит зависимость тестов от порядка
go test -race -p 1 ./...         # когда пакеты делят одну БД

go test -coverprofile=cover.out ./... && go tool cover -html=cover.out
```

`-race` — не опция для конкурентного кода. Детали флагов сборки и линтеров — в `go-quality`,
профилирование и бенчмарки — в `go-profiling`.

Протокольные тесты (SIP/RTP/WebRTC и прочее, где поведение задано стандартом) обязаны
ссылаться на норму — правило и памятка по RFC в `references/protocol-tests.md`.

## Чеклист

- [ ] Вид теста выбран по таблице, а не «как проще».
- [ ] Стабы только там, где систему нельзя поднять; репозитории и шина — реальные.
- [ ] БД-тест делает `t.Skip` без DSN; изоляция выбрана по числу соединений.
- [ ] В `RunInTx` репозитории используют переданный `ctx`.
- [ ] Логика с таймерами — под `synctest.Test`; таймауты инъектированы, не хардкод.
- [ ] Уборка через `t.Cleanup`, не `defer` в хелпере.
- [ ] Из не-тестовых горутин нет `require`/`t.FailNow`.
- [ ] Негативная ветка проверяет и код ответа, и отсутствие побочки.
- [ ] Паника прод-кода изолирована `recoverAsFailure`.
- [ ] Прогнано под `-race` и `-count=1`.
