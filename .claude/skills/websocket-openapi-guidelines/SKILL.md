# WebSocket-контракт в OpenAPI

## Сначала — а точно OpenAPI?

OpenAPI создан для HTTP-запросов и ответов, и стандартного отображения на WebSocket
у него нет. Всё, что ниже, — обходной приём: спека описывает **типы сообщений**, а сам
протокол (порядок, кто когда шлёт, что происходит при разрыве) живёт в прозе.

**Сперва рассмотри AsyncAPI** — он для событийных и потоковых контрактов и есть
и генераторы под Go, и под TypeScript. Причина остаться на OpenAPI обычно одна:
у продукта уже есть HTTP-спека и общий пайплайн кодогенерации, и заводить второй
формат дороже, чем терпеть обходной приём. Это законная причина, но пусть она будет
осознанной.

Версия документа — `openapi: 3.1.0`. Именно в 3.1 схемы выровнены с JSON Schema
(`const`, нормальные дискриминаторы `oneOf`), а на 3.0 приходится изображать
дискриминатор через enum с одним значением.

## Отношение к openapi-rpc-conventions

Основные конвенции API — там. Здесь только отличия, и каждое названо явно:

| Тема | Правило HTTP | Здесь |
|---|---|---|
| Метод | только POST | **`get:` на эндпоинте апгрейда** — единственное исключение: handshake WebSocket по RFC 6455 это и есть HTTP GET, отвечающий `101` |
| operationId | первая буква строчная | так же (`connectWebSocket`, `internalWebSocketMessages`) |
| Имена схем | `<OperationId>Input`/`Output`, wire DTO — `Nwk*` | у сообщений своё семейство: `{Entity}Message` и `{Entity}Payload`. Префикс `Nwk` к ним не применяется, но **правило слоя действует без изменений**: это wire-формат, в usecase и домен он не протекает, конвертируют мапперы |
| Регистр полей | camelCase | camelCase — **так же**. Историческая snake_case в существующих ws-спеках остаётся, но новые поля так не заводим: две системы именования в одном продукте дороже, чем разовое расхождение |

## Единый конверт

Все сообщения — одной формы: `type`, `payload`, и `timestamp` у сообщений сервера.

```yaml
IncomingCallMessage:
  type: object
  description: Уведомление о входящем звонке.
  required: [type, payload, timestamp]
  properties:
    type:
      type: string
      const: incoming_call
    payload:
      $ref: '#/components/schemas/IncomingCallPayload'
    timestamp:
      type: string
      format: date-time
```

Правила, каждое со своей причиной:

- **`type` — ровно одно допустимое значение** (`const` в 3.1, `enum` с одним элементом
  в 3.0). Это дискриминатор: генератор выпускает отдельный тип на сообщение, а не один
  тип с полем-строкой, и разбор на клиенте становится исчерпывающим по switch.
- **`payload` — всегда `$ref` на отдельную схему**, никогда не инлайн. Иначе поля
  расползаются по конверту и схему нельзя переиспользовать.
- **`timestamp` только у сервер → клиент.** Часы клиента не синхронизированы, его
  временная метка не значит ничего и только провоцирует по ней сортировать.
- **`required` перечисляем явно.** По умолчанию в JSON Schema всё необязательно, и
  генератор выпустит указатели на все поля.

Значения `type` — snake_case (`incoming_call`, `call_ended`). Это значения, а не имена
полей, и они попадают в логи и метрики как есть.

## Разделение по направлению

Схемы группируются по направлению, с комментарием-разделителем: сервер → клиент и
клиент → сервер живут в разных блоках. Одно и то же имя сообщения в обе стороны — почти
всегда ошибка моделирования.

```yaml
components:
  schemas:
    # ===== СЕРВЕР → КЛИЕНТ =====
    IncomingCallMessage: { }
    CallEndedMessage: { }

    # ===== КЛИЕНТ → СЕРВЕР =====
    AuthMessage: { }
    PingMessage: { }
```

## Фиктивный эндпоинт для кодогенерации

Ключевой приём. Генераторы не выпускают типы из `components/schemas`, на которые никто
не ссылается: обход идёт от эндпоинтов. Схемы сообщений, не привязанные ни к какому
запросу, просто не попадут в сгенерированный код.

Лечится эндпоинтом, который существует только ради обхода: `requestBody` перечисляет
через `oneOf` всё, что шлёт клиент, `responses` — всё, что шлёт сервер.

```yaml
/internal/ws-messages:
  post:
    operationId: internalWebSocketMessages
    summary: Типы WebSocket-сообщений (только для кодогенерации)
    description: |
      В рантайме не используется и не роутится.
      Существует, чтобы генератор выпустил типы всех сообщений.
    tags: [Internal]
    requestBody:
      required: true
      content:
        application/json:
          schema:
            oneOf:
              - $ref: '#/components/schemas/AuthMessage'
              - $ref: '#/components/schemas/PingMessage'
    responses:
      '200':
        description: OK
        content:
          application/json:
            schema:
              oneOf:
                - $ref: '#/components/schemas/IncomingCallMessage'
                - $ref: '#/components/schemas/CallEndedMessage'
```

Префикс `/internal/` и предупреждение в `description` — обязательны: иначе следующий
читатель попробует его вызвать. Роутер на него вешать не нужно.

Цена приёма — список надо руками держать в актуальном состоянии. Забыли добавить
сообщение — тип не сгенерируется, и заметится это уже в коде.

## Эндпоинт апгрейда

Описывается ради адреса, заголовков и авторизации, а не ради тела:

```yaml
/ws/operator:
  get:
    operationId: connectWebSocket
    summary: Установка WebSocket-соединения
    description: |
      Апгрейд до WebSocket (RFC 6455). После установки соединения клиент обязан
      прислать AuthMessage; иначе сервер разрывает соединение по таймауту.
    responses:
      '101':
        description: Switching Protocols
      '401':
        description: Неавторизован
```

Единственное место, где в этих конвенциях допустим `get:`, — и именно потому, что
handshake по RFC 6455 и есть HTTP GET.

## Чеклист нового сообщения

1. Схема `{Entity}Message`: `type`, `payload`, `timestamp` (если сервер → клиент).
2. Схема `{Entity}Payload` с данными, `required` перечислены.
3. `type` — одно значение, snake_case.
4. `payload` через `$ref`.
5. Сообщение добавлено в `oneOf` фиктивного эндпоинта — в ту сторону, в которую ходит.
6. Поведение (когда шлётся, что делать при разрыве) описано в `description`.

## Антипаттерны

- **Поля в конверте вместо payload** — `call_id` рядом с `type`. Конверт перестаёт быть
  единым, разбор на клиенте становится частным случаем на каждое сообщение.
- **Несколько значений в `type` одной схемы** — генератор выпустит один тип с полем-строкой
  вместо набора типов, и весь смысл дискриминатора теряется.
- **Нет `timestamp` у сообщения сервера** — событие невозможно упорядочить при разборе
  инцидента.
- **Сообщение не добавлено в фиктивный эндпоинт** — тип молча не сгенерируется.
- **Описание протокола только в схемах** — порядок сообщений, таймауты и поведение при
  разрыве в схемы не помещаются; им место в `info.description` или в отдельном документе.
